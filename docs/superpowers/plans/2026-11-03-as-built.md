## Differences from the plans

**Part A**
- Inventory and vouchers are per **product**, not per lot (`lot_id` was dropped from the tables). Lots keep moving through `LotService` as before.
- Voucher numbering and inventory numbering share `warehouse.voucher_counters` (type `inventory`).
- The freeze guard sits in `StockService` write paths: receive, issue (and therefore transfer and quarantine moves), adjust, production movement, send/consume in production. `adjust_stock(_from_inventory=True)` is the only bypass and is not exposed over HTTP.
- `GET /warehouse/valuation` and `/warehouse/reports/movements` export CSV or XLSX through the new shared `core/tabular_export.py`.
- A "create issue from order" button exists on confirmed sales orders; it drafts the voucher (`SalesOrderService.get_order` was added for it).

**B1** — frontend create form is header-only (no line editor); the API accepts lines.

**B3** — receipts and disbursements share one set of tables (`treasury.documents`, `document_allocations`, `document_payments`, `instruments`). Documents post on creation (no draft step).
- Over-allocation is checked against what posted documents already committed, not only the invoice's `amount_paid`, because the owning module updates that figure asynchronously from our events. Documents allocating to the same invoice are serialised with an advisory lock.
- `core/atomic.py` (`@atomic`) wraps multi-row postings in a savepoint so a refusal leaves no partial rows even when the caller keeps its transaction.

**B4** — a cheque marked unpaid debits the account only if it had been collected first; rejected while pending, it moves no balance. Bounces are limited to cheques. Unpaid reduces the paid amount on the invoices the document was allocated to, in invoice-id order, never beyond what each allocation still stands for.

**B5** — the upload endpoint takes the file as base64 JSON (`POST /treasury/statements/import`, `commit=false` previews) because the backend has no multipart support. `.xlsx` and `.csv`/`.txt` are accepted.

## Decisions still open
- The accountant must confirm every ledger account named in `2026-11-03-b6-ledger-posting.md` before any posting is written.
- Whether a bounced cheque rejected *before* the bank credited it should be recorded as a charge is not decided; today it moves nothing.
- Cash payment ceiling: none enforced (configurable in Settings).

## Operational notes
- The worker must be restarted to register the new finance and procurement consumers (`treasury.receipt.*`, `treasury.disbursement.*`, `treasury.instrument.unpaid`). Until it runs, invoices keep their old paid status, although treasury already refuses over-allocation.
- Dev data: `python -m scripts.seed_treasury_demo` creates a demo bank, three accounts, a partly paid sales invoice, a supplier invoice and a pending cheque for the `demo` tenant (idempotent).
- New permissions are not auto-granted; the demo user was granted them through the API in the development database.
